# Video Multimodal Search Task Tracker

## Objective

Extend the existing video search feature so retrieval can use both text-based segment embeddings and direct multimodal embeddings from `voyage-multimodal-3.5`, instead of relying only on segment title, description, transcript, tags, and metadata text.

## Feature Summary

Current video semantic search stores one text embedding per `video_segments` document in `embedding`, generated from segment metadata and transcript-like text with `voyage-4-large`.

The target feature adds a visual/multimodal retrieval path:

- Keep the existing text embedding flow as a stable baseline.
- Generate a new multimodal embedding for each searchable video segment clip.
- Store multimodal vectors separately from existing text vectors.
- Create a dedicated Atlas Vector Search index for multimodal vectors.
- Add a UI/API mode that can search by query text against multimodal video embeddings.
- Optionally fuse text semantic, keyword, and multimodal results in hybrid mode.

## Key Design Decision

Preferred implementation: segment-level multimodal embeddings.

Reason:

- The current UI demonstrates segment-level retrieval and timestamp jump.
- Full-video embeddings would return only the overall video and weaken timestamp precision.
- Segment-level multimodal vectors keep existing playback UX intact.

MongoDB AI Gateway validation selected `video_clip` as the implementation strategy. Full source videos can exceed context limits, so indexing generates short, low-resolution clips from each segment before calling `voyage-multimodal-3.5`.

Current segmentation and embedding rules:

- `seed-video-segments.mjs` reads actual source duration with `ffprobe`.
- Each source video is split into fixed 50-second `video_segments` windows.
- A trailing segment shorter than 2 seconds is merged into the previous segment to avoid invalid clips.
- `index-video-segments-multimodal.mjs` sends only `video_base64` clip content to `voyage-multimodal-3.5`.
- Multimodal embedding does not include title, description, transcript, tags, product line, language, or source type.

## Proposed Data Model Changes

Add these fields to `video_segments`:

| Field | Type | Purpose |
|---|---|---|
| `multimodalEmbedding` | `number[]` | Vector generated by `voyage-multimodal-3.5`. |
| `multimodalEmbeddingModel` | `string` | Model name, expected `voyage-multimodal-3.5`. |
| `multimodalEmbeddingDimensions` | `number` | Actual vector dimension returned by the API. Must be measured before index creation. |
| `multimodalEmbeddingStatus` | `string` | `ready`, `pending`, `failed`, or `unsupported`. |
| `multimodalEmbeddingSource` | `string` | `video_clip`, `full_video`, or `keyframes`. |
| `multimodalEmbeddedAt` | `Date` | Last successful multimodal embedding timestamp. |
| `multimodalEmbeddingError` | `string` | Sanitized error message for failed rows. |

Do not overwrite existing `embedding`; it remains the text embedding baseline.

## Proposed Atlas Indexes

Create a new vector index on `video_segments`:

Index name: `video_multimodal_vector_index`

Initial definition shape:

```json
{
  "fields": [
    {
      "type": "vector",
      "path": "multimodalEmbedding",
      "numDimensions": "<measured from voyage-multimodal-3.5>",
      "similarity": "cosine"
    },
    { "type": "filter", "path": "productLine" },
    { "type": "filter", "path": "tags" },
    { "type": "filter", "path": "language" },
    { "type": "filter", "path": "sourceType" },
    { "type": "filter", "path": "videoId" }
  ]
}
```

The current `video_vector_index` remains unchanged for text embeddings.

## Open Questions

1. Should the first implementation embed segment clips or full videos?
2. If direct video upload is unsupported, is keyframe-based multimodal embedding acceptable?
3. Should existing `hybrid` include multimodal signals, or should we add a separate `multimodalHybrid` mode first?
4. Should multimodal embeddings be generated for every segment or only for longer/high-value segments to reduce cost?
5. Do we need to cache temporary clips/keyframes on disk, or should they be generated and deleted during indexing?

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| `voyage-multimodal-3.5` does not accept raw video payloads through current endpoint/key. | Feature blocked or requires alternative input strategy. | Validate endpoint first; fall back to sampled keyframes only if approved. |
| Multimodal output dimension differs from current 1024 text embeddings. | Atlas index cannot be created with guessed dimensions. | Measure dimension before index creation and store dimension metadata. |
| Full-video embeddings reduce timestamp precision. | Demo becomes less compelling. | Prefer segment-level clips or keyframes. |
| Video payloads are large. | API failures, slow indexing, higher cost. | Clip per segment, limit duration, batch carefully, and mark failures per segment. |
| Hybrid scoring becomes confusing. | Harder to explain in customer demo. | Keep separate `multimodal` mode first; add transparent score breakdown for fusion. |
